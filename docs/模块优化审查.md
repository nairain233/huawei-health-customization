# 模块优化审查

审查日期：2026-10-02。范围：当前工作区的 Hook 编排、布局工具、扫描与缓存、配置读写、测试和构建流程。第 1–10 节保留首轮优化前的审查证据；后续实际变更与最新验证见“实施记录”。

## 结论与排序

优先补齐异步失败隔离与服务配置确认，再处理布局复用和扫描开销。现有进程守卫、独立服务开关、后台扫描、定位缓存及布局配置协调器应保留；不为了代码整齐引入新的扫描框架或通用配置框架。

| 顺序 | 优化点 | 证据 | 收益 | 修改风险 / 验证成本 |
| --- | --- | --- | --- | --- |
| 1 | 异步布局回调隔离异常 | 生产字节码独立复现 | 防止模块回调异常传播到宿主并中断其他功能 | 中 / JVM 控制流测试和设备页面回归 |
| 2 | 服务配置的确认状态与不确定绑定保护 | 完整代码调用链 | 避免显示未确认值、通过普通刷新重新启用不确定配置 | 中 / 可控执行器、失败偏好与生命周期测试 |
| 3 | 观察器注册随 Hook 事务激活和撤销 | 完整代码调用链 | 安装失败后确实保持原行为 | 中 / 安装失败、排队回调和能力缺失测试 |

| 6 | 扫描进度合并发布 | 生产扫描和代码调用链 | 减少原子文件写入、完整 JSON 编码和 Provider 同步调用 | 低到中 / 假时钟、终态及中断恢复测试 |

| 10 | 增加 PR 验证及设备测试源码编译 | 工作流只在 main push / 手动运行，缺少相应任务 | 尽早发现测试编译、元数据和作用域回归 | 低 / CI 工作流检查 |

“独立复现”使用现有生产 `classes.jar` 与最小 Android 替身，或现有内存偏好测试类；只证明控制流和存储行为，不代表 LSPosed 或设备回归已通过。性能候选不宣称已经测得卡顿或具体提速比例。

## 1. 异步布局回调隔离异常

位置：`hook/util/PageLayoutObserver.kt:32`、`hook/util/ActivePageObserver.kt:24,32`，以及设备、运动功能中的 `View.post` 回调。

当前 `ExceptionMode.PROTECTIVE` 位于 Hook 拦截器；稍后通过 Handler/View 执行的任务，以及 Application 生命周期监听器，是另外的调用路径。观察器直接执行页面处理闭包，没有局部异常保护。

独立复现直接调用当前生产类，得到：

```text
PAGE_CALLBACK_EXCEPTION_ESCAPED: true
ACTIVITY_CALLBACK_EXCEPTION_ESCAPED: true,nextListenerCalls=0
```

一个监听器抛出异常后，异常向外传播，后面的监听器没有执行。具体宿主页面是否产生这种异常仍须设备验证，但当前控制流缺口已经确认。

建议统一异步执行入口，逐个监听器隔离错误；同一失败源限次记录固定功能 ID 和异常类型，停用或撤销该源，保留其他监听器。原宿主方法抛出的异常不应被当成模块异常吞掉。避免重复布局时反复抛错或刷日志。

验收：故障闭包不向外抛出；其他监听器继续执行；首次回放、普通恢复和 post 路径都覆盖；页面销毁后不执行失效任务；日志不包含宿主业务参数或异常消息。

## 2. 服务配置确认与绑定状态

位置：`app/ServiceBlockActivity.kt:68,94,108,120`。对照：`app/LayoutSettingsCoordinator.kt`、`app/ScanStatusController.kt`。

当前存在三个关联行为：

- 保存开始时立即 `state.copy(config = next, saving = true)`，开关及有效数量先显示尚未确认的值。
- 保存和回滚都失败时，只设置 `connected=false`；没有记录产生不确定状态的服务绑定身份。
- 普通刷新成功读取后，以 `config != null` 恢复 `connected=true`。同一 RemotePreferences 的本地缓存读成功，不能证明失败的持久化已经恢复。

另外，配置状态和单线程执行器属于 Activity；返回重进或语言/方向重建会创建新实例，而旧实例已开始的提交仍可能继续。单个 Activity 的 revision 能丢弃旧 UI 回调，无法串行管理新旧实例的配置操作，也无法跨页面保留不确定绑定状态。

建议参照布局协调器的已确认状态和绑定身份规则，增加应用级服务配置协调器。业务配置只在 commit 成功后更新；保存过程中保留已确认值并禁用编辑；不确定状态在同一绑定内持续有效，直到新绑定成功读取后恢复。页面只订阅状态和发出操作。

复用已经证明有效的状态模型与测试手法即可；不把布局、服务、扫描预约强行合成一套泛型框架。

验收：保存排队、服务断开、旧结果晚到、刷新与保存交错、返回重进和重建后均保持一致；保存及回滚失败后，普通刷新不恢复编辑，新服务绑定才可以恢复。

## 3. 观察器需要加入安装事务

位置：`hook/feature/SportPageFeature.kt:44`、`hook/feature/DevicePageFeature.kt:46`、`hook/TransactionalHooks.kt:15`。

运动功能在 Hook 注册前安排 `ActivePageObserver.observe`；如果随后 Hook 安装失败，事务只撤销 HookHandle，已经排队的监听器仍可注册并执行。设备功能即使全部安装失败、最终返回 Unsupported，也会注册 Activity 观察器。

这意味着“安装失败保持原界面”目前未覆盖观察器副作用。观察器不能只根据某个共享配置键已匹配就对整个页面执行所有规则，应同时限定实际通过校验和安装成功的功能组。

建议在事务成功后激活观察器，提供可撤销句柄；回滚时撤销注册和待执行任务，残留回调检查激活状态。按安装成功的组限定页面回放范围。

验收：注入首个/中间 Hook 注册失败后，页面回放没有修改；旧设备页共享键成功、新 Arkui 组失败时，不激活失败组的页面处理；成功组仍独立生效。

## 4. 重复折叠与 View 重绑定

位置：`hook/util/ViewTrimmer.kt:22`。相关恢复入口：`SportPageFeature.applyBoundQuickEntry` 和 `ViewSelectors.collapseContainersByText`。

当前把“存在快照”等同于“实际仍然折叠”，因此再次调用直接返回。宿主在同一个 View 上重新设置可见性和布局参数后，观察器即使再次调用 collapse，也不会重新隐藏。

独立复现步骤：原尺寸 120×80 → 折叠 → 宿主设为 VISIBLE 和 240×160 → 再折叠。实际结果：

```text
RECOLLAPSE_AFTER_HOST_RESET: visibility=0,width=240,height=160
```

建议区分原始快照与当前隐藏状态：快照只在首次处理时记录，重复应用核对实际状态，仅在偏离时重新折叠，避免每次 global layout 都 requestLayout。恢复不能覆盖最初快照。

同步检查快捷入口标题后备：它只隐藏、不主动恢复，当前恢复依赖独立绑定 Hook。该绑定入口失效时，不能继续启用可能污染复用项的后备行为。

验收：隐藏→宿主刷新→再次隐藏一致；隐藏项重绑定为可见项恢复；未知标题保持显示；尺寸、边距和 RTL 可恢复；重复布局不产生循环或持续请求布局。

## 5. 服务保存失败应恢复原始存储快照

位置：`config/ServiceConfigStore.kt:20`、`config/ServiceBlockConfig.kt:65`。对照：`config/LayoutConfigStore.kt`。

当前回滚写入的是经过解析、规范化的 ServiceBlockConfig，无法恢复原始键的存在状态或被读取层忽略的原始值。现有测试只比较解析结果，未比较完整偏好快照。

独立程序直接调用生产 ServiceConfigStore，使用与现有测试一致的“本地缓存先更新、首次 commit 返回 false、第二次返回 true”偏好替身：

```text
before={}
after={service_block.enabled=false, service_block.components=[], service_block.presets=[], service_block.debug_mode=false}

before={service_block.presets=[sleep]}
after={service_block.presets=[], service_block.enabled=false, service_block.components=[], service_block.debug_mode=false}
```

这些结果的当前有效配置可相同，但原始存储已改变。未知旧规则可以在成功的正常保存时清理，失败回滚不应顺便执行清理。

建议提交前保存实际涉及键的存在状态和原始值，失败时恢复这些原始值或 remove 原本不存在的键。集合必须复制，其他配置键保持原值。结合第 2 项处理回滚失败后的编辑保护。

验收：保存前后 `preferences.all` 精确一致；缺键、未知旧预设、无效组件和无关布局/扫描键都覆盖；第二次 commit 失败必须报告状态不确定。

## 6. 合并扫描进度发布

位置：`scan/LayoutScanner.kt:167`、`scan/ScanRuntime.kt:42`、`scan/ScanReportProvider.kt:32`。

每次扫描进度回调都完整生成报告，先写目标进程的原子文件，再执行 Provider call；Provider 接收后同步 commit。一次发布还重复调用 report.encode。扫描中很多单项共用同一功能组定位，但进度仍逐项发布。

建议在扫描工作线程按时间合并中间进度，单次发布复用已编码 JSON。开始、完成和失败必须立即发布；序号可以递增跳号，但 checked 集合保持单调；终态和请求确认不能被节流延后或丢失。

验收：使用假时钟确认快速连续回调只发布必要中间态；完整终态、缓存命中、Provider 不可用、进程中断和下次重传行为保持正确。先记录调用次数与累计发布耗时，再给出优化收益。

## 7. 缓存命中前仍读取完整 APK

位置：`scan/ScanRuntime.kt:58,63`、`scan/ApkIdentity.kt:8`。

缓存读取之前先对 base/split 的完整内容计算 SHA-256。本地基准 APK 为 269,088,857 字节，约 256.6 MiB；每次目标进程启动，即使最终命中定位缓存，也会执行全量读取。工作线程避免直接阻塞主线程，但不能消除 CPU/I/O 竞争或延后 Hook 安装的成本。

完整内容身份是现有缓存正确性的重要保证，不能仅凭文件大小或 mtime 相同就宣称可安全跳过 SHA-256。

建议先拆分记录身份计算、缓存读取、描述符复核、Dex 扫描、报告发布和安装耗时，设备上比较首次启动/缓存/预约重扫。优先评估后台线程调度与报告开销；只有测量证明哈希仍为瓶颈，且明确保留更新、降级、split、规则版本和请求失效边界后，再讨论分层身份缓存。

## 8. 反射与页面遍历

位置：`hook/resolver/ReflectionTargets.kt:40,61`、`hook/util/ViewSelectors.kt`、`SportPageFeature.applyPageViews`。

invokeNoArgs 每次枚举类继承链的 declaredMethods；我的列表的多轮过滤、分组清理和运动区块识别都会重复调用。fieldValue 同样重复枚举字段。页面全局布局观察还会重复按资源定位和整树遍历。

建议分别测量调用频率和耗时，先缓存已经确认的访问器，按类、名称、签名和别名映射隔离；别名变更时清理缓存，不共享错误的重载。失败命中也可以缓存，但必须能区分正常 null 与解析失败并限次诊断。视图只按当前页面/区块查找，若缓存 View 使用弱引用并在重建/重绑定后重新核验。

禁止为了这一项引入复杂扫描器，禁止持有 Activity、Fragment 或 View 静态强引用。没有设备采样前，不承诺帧率收益。

## 9. 服务使用文档存在差异

位置：`README.md:32,39`、`app/ServiceBlockScreen.kt`、`ServiceBlockConfig.effectiveComponents`。

README 仍以进入服务页后直接搜索逐项选择为主要操作步骤，当前实际是业务分组页，自定义服务入口需要调试模式。README 还称“仅显示已保存配置”，而当前 ServiceBlockActivity 会乐观显示待保存值。

后续实现应先修正状态行为，再同步用户需要知道的业务分组、核心影响确认、调试模式和自定义规则暂停行为。保留实际业务影响待验证的边界；业务组不能被描述为已证实安全关闭。开发验证记录继续放 docs/AGENTS，不追加到 README。

## 建议实施批次

1. **失败隔离**：第 1、3 项，先覆盖故障注入与观察器事务，再接入设备/运动页面。
2. **服务配置**：第 2、5 项，以应用级协调器保存确认状态和原始快照；随后同步第 9 项用户说明。
3. **布局恢复**：第 4 项，以实际 View/列表重绑定验证隐藏和恢复。
4. **扫描开销**：先完成第 6 项并记录耗时，再据第 7、8 项的设备数据决定缓存与遍历优化。
5. **维护验证**：第 10 项，并在有连接设备后补齐当前运行时验证边界。

遵循 KISS：优先修具体状态和异常边界。遵循 DRY：异步安全执行与确认式存储确有重复时才复用。遵循 YAGNI：不扩大 Hook 范围、不升级核心依赖、不引入通用框架。保持职责分离：配置页面展示状态，协调器处理读写，Hook 功能处理宿主界面。

## 实施记录

### 第一批：异步失败隔离与观察器事务（2026-10-02）

已实现第 1、3 项涉及的设备/运动页面观察器与显式排队任务保护，并补齐功能组内配置键的授权边界；实际设备验收仍待完成。

- 新增轻量 `LayoutCallbackScope`，每个安装组独立持有激活状态、延迟注册和撤销任务。安装成功且实际注册数量大于 0 才激活；安装失败或无入口时丢弃观察器注册并逆序撤销 Hook。回调异常停用该组，后续残留 Hook 保持放行。
- Activity 回放、global layout 及设备/运动显式 post 均经过组的异常保护。一个监听器失败不影响其他组；同一根 View 可由不同组独立观察。脱离窗口时注销布局监听器、取消排队任务；同一 View 再次挂载后可以重新观察。
- 队列与撤销闭包使用 View 弱引用；已完成任务和已脱离页面会注销撤销记录。Activity 仍使用弱引用，销毁或结束的 Activity 不接收回放。
